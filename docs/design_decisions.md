# Fly-in Design Decisions

この文書は、Fly-inの設計上の意思決定を簡潔かつ明確に記録する。
実装の詳細ではなく、「何を採用したか」「なぜ採用したか」を残す。

## 更新ルール

- 新しい設計を実装する前に、選択肢、利点、欠点を壁打ちする。
- 明確に合意した設計だけを「確定事項」へ追加する。
- 合意していない設計判断を実装へ追加しない。
- 設計変更時は既存項目を書き換えるだけでなく、変更理由も記録する。
- 未決定事項は「保留事項」へ記録し、確定事項と混在させない。
- 小さな内部実装であっても、外部挙動、不変条件、責務分担に影響する場合は
  事前に確認する。

## 確定事項

### DD-001: 学習を優先した開発手順

- **決定**: 壁打ちで設計を理解・合意してから実装する。
- **決定**: 明確な実装指示があるまではコードやファイルを変更しない。
- **理由**: 一度に実装を進めず、各設計判断とコードの対応を理解できるように
  するため。

### DD-002: Pythonと開発環境

- **決定**: Python 3.10以上で動作するコードを書く。
- **決定**: ローカル開発には`.venv`、`pip`、`requirements-dev.txt`を使う。
- **決定**: `uv`やPoetryなどのプロジェクト管理ツールは使用しない。
- **決定**: 開発ツールとして`flake8`、`mypy`、`pytest`を使用する。
- **理由**: 課題要件を満たしつつ、環境構築を単純に保つため。

### DD-003: ソースコードの配置

- **決定**: `src/`レイアウトは使用しない。
- **決定**: リポジトリ直下の`fly_in/`をPythonパッケージとして使用する。
- **理由**: パッケージング設定を増やさず、ソースコードを整理するため。

### DD-004: 静的情報と動的状態を分離する

- **決定**: `Zone`、`Connection`、`DroneMap`はマップの静的情報を扱う。
- **決定**: ドローン位置、現在のゾーン占有数、現在の接続使用数などは、
  後で別のシミュレーション状態として扱う。
- **理由**: マップ定義とターンごとに変化する状態を混在させないため。

### DD-005: IDと名前を分離する

- **決定**: ゾーンと接続には内部参照用の整数IDを用意する。
- **決定**: ゾーン名はIDとは別の表示・入力用データとして保持する。
- **理由**: 内部参照と入力上の名前を分離し、名前変更が参照関係へ影響しない
  ようにするため。

### DD-006: `ZoneRole`と`ZoneType`を分離する

- **決定**: `role`はマップ内での役割を表す。
  - `START`
  - `END`
  - `REGULAR`
- **決定**: `zone_type`は進入時の移動特性を表す。
  - `NORMAL`
  - `PRIORITY`
  - `RESTRICTED`
  - `BLOCKED`
- **理由**: 「何のための場所か」と「進入時に何が起きるか」は独立した概念
  だから。

### DD-007: `Zone`が保持するデータ

- **決定**: `Zone`は次のデータを保持する。
  - `id`
  - `name`
  - `x`
  - `y`
  - `role`
  - `zone_type`
  - `max_drones`
  - `color`
- **決定**: スタートとゴールの無制限容量は`max_drones=None`で表す。
- **決定**: 現在滞在しているドローンは`Zone`に保持しない。
- **理由**: `Zone`を静的なゾーン定義に限定するため。

### DD-008: `Zone`の公開メソッド

- **決定**: 次のメソッドを持つ。
  - `is_accessible() -> bool`
  - `movement_cost() -> int | None`
  - `has_unlimited_capacity() -> bool`
- **決定**: `movement_cost()`は次を返す。
  - `NORMAL`: `1`
  - `PRIORITY`: `1`
  - `RESTRICTED`: `2`
  - `BLOCKED`: `None`
- **理由**: いずれも`Zone`自身の情報だけで回答できる処理だから。

### DD-009: 移動コストは移動先ゾーンで決まる

- **決定**: 接続ではなく、移動先の`ZoneType`から移動コストを決める。
- **結果**: 同じ双方向接続でも、方向によって移動コストが異なる場合がある。
- **理由**: 課題仕様が移動先ゾーンの種別を基準にしているため。

### DD-010: `PRIORITY`の扱い

- **決定**: `PRIORITY`の移動コストは`NORMAL`と同じ1ターンとする。
- **決定**: 総移動コストが同じ候補では`PRIORITY`を通る経路を優先する。
- **決定**: より長い経路を、`PRIORITY`を含むという理由だけで選ばない。
- **理由**: `PRIORITY`は絶対条件ではなく、同条件時の優先要素だから。

### DD-011: `Connection`が保持するデータ

- **決定**: `Connection`は次のデータを保持する。
  - `id`
  - `zone_a_id`
  - `zone_b_id`
  - `max_capacity`
- **決定**: 接続は双方向なので、`from`と`to`ではなく`zone_a`と`zone_b`
  で表す。
- **決定**: 現在通過しているドローンは`Connection`に保持しない。
- **理由**: `Connection`を静的な接続定義に限定するため。

### DD-012: `Connection`の公開メソッド

- **決定**: 次のメソッドを持つ。
  - `connects(zone_id) -> bool`
  - `other_zone(zone_id) -> int`
- **決定**: 接続に含まれないIDを`other_zone()`へ渡した場合は
  `ValueError`とする。
- **理由**: 無関係なゾーンIDは通常状態ではなく、呼び出し側の誤りだから。

### DD-013: 完成したマップは変更しない

- **決定**: パーサーは`Zone`と`Connection`を一時的なコレクションへ
  格納し、読み込み完了後に`DroneMap`を構築する。
- **決定**: 完成した`DroneMap`へゾーンや接続を追加・削除しない。
- **理由**: シミュレーション中にマップ定義は変化せず、不完全な`DroneMap`を
  外部へ公開する必要もないため。

### DD-014: `DroneMap`の公開メソッド

- **決定**: 次の汎用的な問い合わせメソッドを持つ。
  - `has_zone(zone_id) -> bool`
  - `get_zone(zone_id) -> Zone`
  - `get_zone_id_by_name(name) -> int | None`
  - `has_connection(connection_id) -> bool`
  - `get_connection(connection_id) -> Connection`
  - `get_connection_between(zone_a_id, zone_b_id) -> Connection | None`
  - `get_connections_from(zone_id) -> list[Connection]`
  - `get_neighbor_ids(zone_id) -> list[int]`
- **決定**: 移動可能先とコストなど、特定用途向けの複合辞書を返すメソッドは
  現時点では追加しない。
- **理由**: `DroneMap`を汎用的なグラフ構造の問い合わせに限定し、経路探索や
  動的容量判定の責務を混在させないため。

### DD-015: 経路探索と移動可否判定を`DroneMap`から分離する

- **決定**: 経路探索用の情報加工は、将来の`Pathfinder`などが担当する。
- **決定**: 現在の占有状況を含む移動可否判定は、将来の`MoveValidator`や
  シミュレーション層が担当する。
- **理由**: 静的な接続関係だけでは、実際にそのターンで移動できるかを判断
  できないため。

### DD-016: 検証責務を入力とマップ構造で分ける

- **決定**: `MapParser`は入力ファイルとしての正しさを検証する。
- **決定**: `DroneMap`は完成したマップ構造としての整合性を検証する。
- **決定**: 入力された1つの値または1つの定義だけで完結する検証は、
  行番号を把握している`MapParser`が担当する。
- **決定**: 複数の`Zone`や`Connection`を組み合わせて初めて判断できる検証は、
  `DroneMap`が担当する。
- **理由**: ファイルの行番号を必要とするエラーと、オブジェクト間の不変条件を
  分離するため。

`MapParser`が担当する検証例:

- 行の構文
- 数値とメタデータの形式・値
- ゾーン名の形式
- ドローン数、容量、ゾーン種別など各定義単体の値
- 接続先がその行より前に定義済みか
- 入力上の重複定義
- 行番号付きエラー

`DroneMap`が担当する検証例:

- ゾーンIDと名前の一意性
- 接続IDの一意性
- 接続の両端が存在すること
- 同じ2ゾーン間の接続が重複していないこと
- スタートとゴールがそれぞれちょうど1つであること

`Zone`と`Connection`自身にも同じローカル不変条件を防御的に持たせるかは、
別の設計事項として保留する。

### DD-017: 専用の検証クラスは現時点で作らない

- **決定**: 現時点では`MapValidator`のような専用クラスを設けない。
- **理由**: 現在の規模では`MapParser`と`DroneMap`の2層で十分であり、
  中間データ構造と処理手順を増やさないため。
- **見直し条件**: 複数入力形式、エラー一括表示、GUI編集などが必要になった
  場合は専用クラスの分離を再検討する。

### DD-018: 追加の検証設計は後で詰める

- **決定**: 現在の`DroneMap`が持つ基本的な構造検証は維持する。
- **決定**: `Zone`と`Connection`の個別値検証、および到達可能性などの
  追加検証は現時点では実装しない。
- **決定**: `MapParser`を設計するときに、入力検証の詳細と重複検証の範囲を
  改めて決める。
- **理由**: データモデルの基本構造を先に固め、実際の入力処理を考える段階で
  必要な検証とエラー情報を具体化するため。

### DD-019: `Scenario`がマップとドローン数をまとめる

- **決定**: `nb_drones`は`DroneMap`に持たせない。
- **決定**: `Scenario`が`DroneMap`とドローン数を保持する。
- **決定**: `Scenario`のデータは`drone_map: DroneMap`と
  `drone_count: int`だけとする。
- **決定**: `Scenario`は`dataclass(frozen=True)`で変更不能にする。
- **決定**: 現時点では`Scenario`に公開メソッドを追加しない。
- **理由**: `DroneMap`は地形・接続構造を表し、ドローン数は今回の実行条件を
  表すため。
- **結果**: 同じ`DroneMap`を異なるドローン数のシナリオで再利用できる。

### DD-020: パーサーの公開入口は1つにする

- **決定**: `MapParser`の公開解析メソッドは`parse_file()`の1つにする。
- **決定**: ファイル読み込み、行の振り分け、ドローン数、ゾーン、接続、
  メタデータの解析は、責務ごとの内部メソッドへ分割する。
- **決定**: 行リストを直接解析するメソッドは、現時点では公開しない。
- **理由**: 利用側のAPIを単純に保ちながら、内部処理の可読性、テスト容易性、
  変更容易性を確保するため。

### DD-021: IDは定義順に採番する

- **決定**: ゾーンIDはゾーンの定義順に1から採番する。
- **決定**: 接続IDは接続の定義順に、ゾーンIDとは別に1から採番する。
- **理由**: 入力ファイルにIDがないため、単純で再現可能な規則を使用する。

### DD-022: 配布マップのテンプレートを厳格に適用する

- **決定**: 配布された全マップで一貫している表記を正規の入力形式とし、
  その形式から外れる空白や区切り表記は受理しない。
- **決定**: 通常の定義行では、行頭・行末空白とタブを許可しない。
- **決定**: 項目間はASCIIスペース1個だけを許可する。
- **決定**: キーワードとコロンは`nb_drones:`、`start_hub:`、
  `end_hub:`、`hub:`、`connection:`の形で一体として扱う。
- **決定**: コロンの直後にはASCIIスペース1個を要求する。
- **決定**: 接続のハイフン前後には空白を許可しない。
- **決定**: メタデータの`=`前後には空白を許可しない。
- **決定**: 複数のメタデータ要素間はASCIIスペース1個とする。
- **決定**: メタデータブロックは本体からASCIIスペース1個空けて行末に置く。
- **決定**: 完全な空行と、行頭が`#`のコメント行だけを無視する。
- **決定**: 空白だけの行、インデントされたコメント、行末コメントは受理しない。
- **理由**: 配布10マップの定義行340件すべてが同じ書式に従っており、
  課題も期待される構造と構文に従わない入力をエラーにするよう求めているため。

### DD-023: ドローン数はパーサーと`Scenario`の両方で検証する

- **決定**: パーサーは`nb_drones`の値を整数へ変換し、1以上であることを
  検証する。
- **決定**: `Scenario`も、インスタンス化に使われる`drone_count`が1以上で
  あることを検証する。
- **理由**: パーサー側の検証は入力ファイルの妥当性を保証し、`Scenario`側の
  検証はパーサーを経由しない生成も含めてオブジェクトの不変条件を保証する。
- **結果**: 同じ数値条件を二重に検証するが、それぞれ異なる境界を保護する。

### DD-024: Fly-in固有エラーに共通の基底クラスを設ける

- **決定**: Fly-in固有の想定内エラーに共通する基底例外として、
  `FlyInError`を設ける。
- **決定**: `FlyInError`自体には追加のデータや処理を持たせない。
- **決定**: 必要になった時点で、用途別の例外クラスを`FlyInError`から
  派生させる。
- **決定**: `FileNotFoundError`などの標準例外や、正常に起こり得る移動失敗は
  無条件に`FlyInError`へ置き換えない。
- **理由**: 呼び出し側がFly-in固有のエラーを一括して扱えるようにしつつ、
  標準例外の意味と通常のシミュレーション結果を区別するため。

### DD-025: `MapParseError`は入力箇所を特定できる情報を持つ

- **決定**: `MapParseError`は`FlyInError`を継承する。
- **決定**: `file_path: Path`と`message: str`を必須情報として保持する。
- **決定**: `line_number: int | None`と`line_text: str | None`を保持する。
- **決定**: 行番号は1始まりとし、`line_text`は末尾の改行だけを除いて、
  入力に含まれる空白やタブを保持する。
- **決定**: 特定の行に原因を限定できないエラーでは、`line_number`と
  `line_text`に`None`を使用する。
- **決定**: 人が読むエラー表示の組み立ては`MapParseError.__str__()`が担当する。
- **決定**: 行番号がある場合は`<path>:<line>: <message>`、ない場合は
  `<path>: <message>`の形式で表示する。
- **決定**: 行本文がある場合は次の行に`> <line_textのrepr表現>`を表示し、
  タブや行末空白などの見えにくい入力も判別できるようにする。
- **決定**: 独自メソッドは`__init__()`と`__str__()`だけとし、通常の公開
  メソッドは設けない。
- **理由**: 複数のマップファイルを連続して処理する場合でも、例外単体から
  対象ファイルと問題箇所を特定できるようにするため。

## 保留事項

以下は未合意または詳細未決定のため、実装前に壁打ちする。

- `Zone`と`Connection`単体で行う値検証の範囲
- `DroneMap`の内部辞書をどの程度厳密に変更不能にするか
- `start_zone_id`と`end_zone_id`を読み取り専用にする具体的な方法
- 高速検索用内部索引の具体的な種類と構築方法
- `MapParser`の具体的なクラス構成と内部メソッド
- パーサーと`DroneMap`で重複して検証する規則の具体的な範囲
- `__init__.py`から公開するクラスの範囲

## 現在の実装との関係

現在のコードには、確定前に追加された内部索引、検証処理、変更防止に関する
実装が含まれている。保留事項を合意するまでは、それらを正式な設計判断とは
見なさない。今後の壁打ち結果に応じて、維持、修正、削除を決める。
