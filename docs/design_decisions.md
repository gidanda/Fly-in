# Fly-in Design Decisions

この文書は、Fly-inの設計上の意思決定を簡潔かつ明確に記録する。
実装の詳細ではなく、「何を採用したか」「なぜ採用したか」を残す。

## 更新ルール

- 新しい設計を実装する前に、選択肢、利点、欠点を壁打ちする。
- 明確に合意した設計だけを「確定事項」へ追加する。
- 合意していない設計判断を実装へ追加しない。
- 設計変更時は既存項目を書き換えるだけでなく、変更理由も記録する。
- 未決定事項は「保留事項」へ記録し、確定事項と混在させない。
- 小さな内部実装であっても、外部挙動、不変条件、責務分担に影響する場合は
  事前に確認する。

## 確定事項

### DD-001: 学習を優先した開発手順

- **決定**: 壁打ちで設計を理解・合意してから実装する。
- **決定**: 明確な実装指示があるまではコードやファイルを変更しない。
- **理由**: 一度に実装を進めず、各設計判断とコードの対応を理解できるように
  するため。

### DD-002: Pythonと開発環境

- **決定**: Python 3.10以上で動作するコードを書く。
- **決定**: ローカル開発には`.venv`、`pip`、`requirements-dev.txt`を使う。
- **決定**: `uv`やPoetryなどのプロジェクト管理ツールは使用しない。
- **決定**: 開発ツールとして`flake8`、`mypy`、`pytest`を使用する。
- **理由**: 課題要件を満たしつつ、環境構築を単純に保つため。

### DD-003: ソースコードの配置

- **決定**: `src/`レイアウトは使用しない。
- **決定**: リポジトリ直下の`fly_in/`をPythonパッケージとして使用する。
- **理由**: パッケージング設定を増やさず、ソースコードを整理するため。

### DD-004: 静的情報と動的状態を分離する

- **決定**: `Zone`、`Connection`、`DroneMap`はマップの静的情報を扱う。
- **決定**: ドローン位置、現在のゾーン占有数、現在の接続使用数などは、
  後で別のシミュレーション状態として扱う。
- **理由**: マップ定義とターンごとに変化する状態を混在させないため。

### DD-005: IDと名前を分離する

- **決定**: ゾーンと接続には内部参照用の整数IDを用意する。
- **決定**: ゾーン名はIDとは別の表示・入力用データとして保持する。
- **理由**: 内部参照と入力上の名前を分離し、名前変更が参照関係へ影響しない
  ようにするため。

### DD-006: `ZoneRole`と`ZoneType`を分離する

- **決定**: `role`はマップ内での役割を表す。
  - `START`
  - `END`
  - `REGULAR`
- **決定**: `zone_type`は進入時の移動特性を表す。
  - `NORMAL`
  - `PRIORITY`
  - `RESTRICTED`
  - `BLOCKED`
- **理由**: 「何のための場所か」と「進入時に何が起きるか」は独立した概念
  だから。

### DD-007: `Zone`が保持するデータ

- **決定**: `Zone`は次のデータを保持する。
  - `id`
  - `name`
  - `x`
  - `y`
  - `role`
  - `zone_type`
  - `max_drones`
  - `color`
- **決定**: スタートとゴールの無制限容量は`max_drones=None`で表す。
- **決定**: 現在滞在しているドローンは`Zone`に保持しない。
- **理由**: `Zone`を静的なゾーン定義に限定するため。

### DD-008: `Zone`の公開メソッド

- **決定**: 次のメソッドを持つ。
  - `is_accessible() -> bool`
  - `movement_cost() -> int | None`
  - `has_unlimited_capacity() -> bool`
- **決定**: `movement_cost()`は次を返す。
  - `NORMAL`: `1`
  - `PRIORITY`: `1`
  - `RESTRICTED`: `2`
  - `BLOCKED`: `None`
- **理由**: いずれも`Zone`自身の情報だけで回答できる処理だから。

### DD-009: 移動コストは移動先ゾーンで決まる

- **決定**: 接続ではなく、移動先の`ZoneType`から移動コストを決める。
- **結果**: 同じ双方向接続でも、方向によって移動コストが異なる場合がある。
- **理由**: 課題仕様が移動先ゾーンの種別を基準にしているため。

### DD-010: `PRIORITY`の扱い

- **決定**: `PRIORITY`の移動コストは`NORMAL`と同じ1ターンとする。
- **決定**: 総移動コストが同じ候補では`PRIORITY`を通る経路を優先する。
- **決定**: より長い経路を、`PRIORITY`を含むという理由だけで選ばない。
- **理由**: `PRIORITY`は絶対条件ではなく、同条件時の優先要素だから。

### DD-011: `Connection`が保持するデータ

- **決定**: `Connection`は次のデータを保持する。
  - `id`
  - `zone_a_id`
  - `zone_b_id`
  - `max_capacity`
- **決定**: 接続は双方向なので、`from`と`to`ではなく`zone_a`と`zone_b`
  で表す。
- **決定**: 現在通過しているドローンは`Connection`に保持しない。
- **理由**: `Connection`を静的な接続定義に限定するため。

### DD-012: `Connection`の公開メソッド

- **決定**: 次のメソッドを持つ。
  - `connects(zone_id) -> bool`
  - `other_zone(zone_id) -> int`
- **決定**: 接続に含まれないIDを`other_zone()`へ渡した場合は
  `ValueError`とする。
- **理由**: 無関係なゾーンIDは通常状態ではなく、呼び出し側の誤りだから。

### DD-013: 完成したマップは変更しない

- **決定**: パーサーは`Zone`と`Connection`を一時的なコレクションへ
  格納し、読み込み完了後に`DroneMap`を構築する。
- **決定**: 完成した`DroneMap`へゾーンや接続を追加・削除しない。
- **理由**: シミュレーション中にマップ定義は変化せず、不完全な`DroneMap`を
  外部へ公開する必要もないため。

### DD-014: `DroneMap`の公開メソッド

- **決定**: 次の汎用的な問い合わせメソッドを持つ。
  - `has_zone(zone_id) -> bool`
  - `get_zone(zone_id) -> Zone`
  - `get_zone_id_by_name(name) -> int | None`
  - `has_connection(connection_id) -> bool`
  - `get_connection(connection_id) -> Connection`
  - `get_connection_between(zone_a_id, zone_b_id) -> Connection | None`
  - `get_connections_from(zone_id) -> list[Connection]`
  - `get_neighbor_ids(zone_id) -> list[int]`
- **決定**: 移動可能先とコストなど、特定用途向けの複合辞書を返すメソッドは
  現時点では追加しない。
- **理由**: `DroneMap`を汎用的なグラフ構造の問い合わせに限定し、経路探索や
  動的容量判定の責務を混在させないため。

### DD-015: 経路探索と移動可否判定を`DroneMap`から分離する

- **決定**: 経路探索用の情報加工は、将来の`Pathfinder`などが担当する。
- **決定**: 現在の占有状況を含む移動可否判定は、将来の`MoveValidator`や
  シミュレーション層が担当する。
- **理由**: 静的な接続関係だけでは、実際にそのターンで移動できるかを判断
  できないため。

### DD-016: 検証責務を入力とマップ構造で分ける

- **決定**: `MapParser`は入力ファイルとしての正しさを検証する。
- **決定**: `DroneMap`は完成したマップ構造としての整合性を検証する。
- **決定**: 入力された1つの値または1つの定義だけで完結する検証は、
  行番号を把握している`MapParser`が担当する。
- **決定**: 複数の`Zone`や`Connection`を組み合わせて初めて判断できる検証は、
  `DroneMap`が担当する。
- **理由**: ファイルの行番号を必要とするエラーと、オブジェクト間の不変条件を
  分離するため。

`MapParser`が担当する検証例:

- 行の構文
- 数値とメタデータの形式・値
- ゾーン名の形式
- ドローン数、容量、ゾーン種別など各定義単体の値
- 接続先がその行より前に定義済みか
- 入力上の重複定義
- 行番号付きエラー

`DroneMap`が担当する検証例:

- ゾーンIDと名前の一意性
- 接続IDの一意性
- 接続の両端が存在すること
- 同じ2ゾーン間の接続が重複していないこと
- スタートとゴールがそれぞれちょうど1つであること

`Zone`と`Connection`自身にも同じローカル不変条件を防御的に持たせるかは、
別の設計事項として保留する。

### DD-017: 専用の検証クラスは現時点で作らない

- **決定**: 現時点では`MapValidator`のような専用クラスを設けない。
- **理由**: 現在の規模では`MapParser`と`DroneMap`の2層で十分であり、
  中間データ構造と処理手順を増やさないため。
- **見直し条件**: 複数入力形式、エラー一括表示、GUI編集などが必要になった
  場合は専用クラスの分離を再検討する。

### DD-018: 追加の検証設計は後で詰める

- **決定**: 現在の`DroneMap`が持つ基本的な構造検証は維持する。
- **決定**: `Zone`と`Connection`の個別値検証、および到達可能性などの
  追加検証は現時点では実装しない。
- **決定**: `MapParser`を設計するときに、入力検証の詳細と重複検証の範囲を
  改めて決める。
- **理由**: データモデルの基本構造を先に固め、実際の入力処理を考える段階で
  必要な検証とエラー情報を具体化するため。

### DD-019: `Scenario`がマップとドローン数をまとめる

- **決定**: `nb_drones`は`DroneMap`に持たせない。
- **決定**: `Scenario`が`DroneMap`とドローン数を保持する。
- **決定**: `Scenario`のデータは`drone_map: DroneMap`と
  `drone_count: int`だけとする。
- **決定**: `Scenario`は`dataclass(frozen=True)`で変更不能にする。
- **決定**: 現時点では`Scenario`に公開メソッドを追加しない。
- **理由**: `DroneMap`は地形・接続構造を表し、ドローン数は今回の実行条件を
  表すため。
- **結果**: 同じ`DroneMap`を異なるドローン数のシナリオで再利用できる。

### DD-020: パーサーの公開入口は1つにする

- **決定**: `MapParser`の公開解析メソッドは`parse_file()`の1つにする。
- **決定**: ファイル読み込み、行の振り分け、ドローン数、ゾーン、接続、
  メタデータの解析は、責務ごとの内部メソッドへ分割する。
- **決定**: 行リストを直接解析するメソッドは、現時点では公開しない。
- **理由**: 利用側のAPIを単純に保ちながら、内部処理の可読性、テスト容易性、
  変更容易性を確保するため。

### DD-021: IDは定義順に採番する

- **決定**: ゾーンIDはゾーンの定義順に1から採番する。
- **決定**: 接続IDは接続の定義順に、ゾーンIDとは別に1から採番する。
- **理由**: 入力ファイルにIDがないため、単純で再現可能な規則を使用する。

### DD-022: 配布マップのテンプレートを厳格に適用する

- **決定**: 配布された全マップで一貫している表記を正規の入力形式とし、
  その形式から外れる空白や区切り表記は受理しない。
- **決定**: 通常の定義行では、行頭・行末空白とタブを許可しない。
- **決定**: 項目間はASCIIスペース1個だけを許可する。
- **決定**: キーワードとコロンは`nb_drones:`、`start_hub:`、
  `end_hub:`、`hub:`、`connection:`の形で一体として扱う。
- **決定**: コロンの直後にはASCIIスペース1個を要求する。
- **決定**: 接続のハイフン前後には空白を許可しない。
- **決定**: メタデータの`=`前後には空白を許可しない。
- **決定**: 複数のメタデータ要素間はASCIIスペース1個とする。
- **決定**: メタデータブロックは本体からASCIIスペース1個空けて行末に置く。
- **決定**: 完全な空行と、行頭が`#`のコメント行だけを無視する。
- **決定**: 空白だけの行、インデントされたコメント、行末コメントは受理しない。
- **理由**: 配布10マップの定義行340件すべてが同じ書式に従っており、
  課題も期待される構造と構文に従わない入力をエラーにするよう求めているため。

### DD-023: ドローン数はパーサーと`Scenario`の両方で検証する

- **決定**: パーサーは`nb_drones`の値を整数へ変換し、1以上であることを
  検証する。
- **決定**: `Scenario`も、インスタンス化に使われる`drone_count`が1以上で
  あることを検証する。
- **理由**: パーサー側の検証は入力ファイルの妥当性を保証し、`Scenario`側の
  検証はパーサーを経由しない生成も含めてオブジェクトの不変条件を保証する。
- **結果**: 同じ数値条件を二重に検証するが、それぞれ異なる境界を保護する。

### DD-024: Fly-in固有エラーに共通の基底クラスを設ける

- **決定**: Fly-in固有の想定内エラーに共通する基底例外として、
  `FlyInError`を設ける。
- **決定**: `FlyInError`自体には追加のデータや処理を持たせない。
- **決定**: 必要になった時点で、用途別の例外クラスを`FlyInError`から
  派生させる。
- **決定**: `FileNotFoundError`などの標準例外や、正常に起こり得る移動失敗は
  無条件に`FlyInError`へ置き換えない。
- **理由**: 呼び出し側がFly-in固有のエラーを一括して扱えるようにしつつ、
  標準例外の意味と通常のシミュレーション結果を区別するため。

### DD-025: `MapParseError`は入力箇所を特定できる情報を持つ

- **決定**: `MapParseError`は`FlyInError`を継承する。
- **決定**: `file_path: Path`と`message: str`を必須情報として保持する。
- **決定**: `line_number: int | None`と`line_text: str | None`を保持する。
- **決定**: 行番号は1始まりとし、`line_text`は末尾の改行だけを除いて、
  入力に含まれる空白やタブを保持する。
- **決定**: 特定の行に原因を限定できないエラーでは、`line_number`と
  `line_text`に`None`を使用する。
- **決定**: 人が読むエラー表示の組み立ては`MapParseError.__str__()`が担当する。
- **決定**: 行番号がある場合は`<path>:<line>: <message>`、ない場合は
  `<path>: <message>`の形式で表示する。
- **決定**: 行本文がある場合は次の行に`> <line_textのrepr表現>`を表示し、
  タブや行末空白などの見えにくい入力も判別できるようにする。
- **決定**: 独自メソッドは`__init__()`と`__str__()`だけとし、通常の公開
  メソッドは設けない。
- **理由**: 複数のマップファイルを連続して処理する場合でも、例外単体から
  対象ファイルと問題箇所を特定できるようにするため。

### DD-025A: マップ構造の不正には`MapDefinitionError`を使う

- **決定**: `MapDefinitionError`を`FlyInError`の派生例外として設ける。
- **決定**: `MapParseError`と`MapDefinitionError`は親子関係にせず、
  `FlyInError`を共通の親とする兄弟クラスにする。
- **決定**: `MapDefinitionError`は追加の位置情報や独自メソッドを持たず、
  例外メッセージだけを使用する。
- **決定**: `DroneMap`構築時のゾーン・接続・ロール間の構造不整合には
  `ValueError`ではなく`MapDefinitionError`を使用する。
- **決定**: マップへの未知IDによる問い合わせの`KeyError`や、
  `Connection.other_zone()`の誤用による`ValueError`は変更しない。
- **理由**: ファイル上の問題と、入力元に依存しないマップ構造の問題を
  区別しながら、どちらも`FlyInError`として一括処理できるようにするため。

### DD-025B: `MapDefinitionError`をパーサーエラーへ変換しない

- **決定**: `parse_file()`は既知の不正入力を`DroneMap`構築前に検出し、
  行情報を持つ`MapParseError`を送出する。
- **決定**: `DroneMap`構築時に`MapDefinitionError`が発生しても、
  `MapParseError`へ捕捉・変換しない。
- **理由**: パーサー経由で`MapDefinitionError`が発生する場合は、パーサーの
  検証漏れまたは両層の不整合であり、入力エラーへ言い換えず発見可能にするため。

### DD-026: `MapParser`は解析結果を保持しない

- **決定**: `MapParser`は解析途中の情報や完成した解析結果を、インスタンスの
  属性として保持しない。
- **決定**: ドローン数、ゾーン、接続、名前検索情報などの途中経過は、
  1回の`parse_file()`呼び出しの内部だけで管理する。
- **決定**: 解析成功後は完成した`Scenario`を返し、呼び出し側は`Scenario`を
  通して読み取られたデータへアクセスする。
- **理由**: ファイル間で解析状態が混ざることを防ぎ、パーサーを入力から
  `Scenario`への変換処理に限定するため。

### DD-027: ドローン数の行解析と行間検証を分離する

- **決定**: `MapParser`は非公開メソッド`_parse_drone_count()`を持つ。
- **決定**: `_parse_drone_count()`はファイルパス、1始まりの行番号、行本文を
  受け取り、検証済みのドローン数を`int`で返す。
- **決定**: `_parse_drone_count()`は`nb_drones: <positive_integer>`という
  1行の構文と、値が1以上であることを検証する。
- **決定**: `_parse_drone_count()`はパーサーの状態を変更せず、値の保存は
  呼び出し元の`parse_file()`が担当する。
- **決定**: `nb_drones`が最初の有効な定義であることと、複数回定義されて
  いないことは、行間の状態を知る`parse_file()`が検証する。
- **理由**: 1行だけで完結する解析と、複数行の順序・重複の管理を分離するため。

### DD-028: メタデータの構文解析を共通化する

- **決定**: `MapParser`は非公開メソッド`_parse_metadata()`を持ち、ゾーンと
  接続の解析処理から共通して呼び出す。
- **決定**: `_parse_metadata()`は`[key=value ...]`という共通構造を検証し、
  メタデータを`dict[str, str]`へ変換する。
- **決定**: 角括弧、項目区切り、`key=value`形式、空のキー・値、キーの重複は
  `_parse_metadata()`が検証する。
- **決定**: 使用可能なキーと値の意味は`_parse_metadata()`では検証しない。
  ゾーン用のキーと値は`_parse_zone()`、接続用のキーと値は
  `_parse_connection()`が検証する。
- **理由**: 共通する構文処理の重複を避けつつ、用途ごとのルールを対応する
  解析メソッドに残すため。

### DD-029: ゾーンの行解析と行間検証を分離する

- **決定**: `MapParser`は非公開メソッド`_parse_zone()`を持つ。
- **決定**: `_parse_zone()`はファイルパス、1始まりの行番号、行本文、
  定義順に決められたゾーンIDを受け取り、検証済みの`Zone`を返す。
- **決定**: `_parse_zone()`は行の構文、ロール、名前の単体書式、整数座標、
  ゾーン用メタデータのキーと値、デフォルト値を処理する。
- **決定**: メタデータがない場合、`zone_type`は`NORMAL`、`color`は`None`、
  通常ゾーンの`max_drones`は1とする。
- **決定**: 開始・終了ゾーンの`max_drones`は常に`None`とし、構文として
  正しい`key=value`であれば指定値の内容は検証せず無視する。
- **決定**: `_parse_zone()`は状態を変更せず、ゾーン名、開始ゾーン、終了ゾーンの
  重複と解析結果の保存は`parse_file()`が担当する。
- **理由**: 1つのゾーン定義だけで判断できる処理と、他の定義との比較や
  解析順序の管理を分離するため。

### DD-030: 接続の行解析と接続間の重複検証を分離する

- **決定**: `MapParser`は非公開メソッド`_parse_connection()`を持つ。
- **決定**: `_parse_connection()`はファイルパス、1始まりの行番号、行本文、
  定義順に決められた接続ID、定義済みゾーンの名前とIDの対応を受け取り、
  検証済みの`Connection`を返す。
- **決定**: `_parse_connection()`は行の構文、異なる2つの接続先、両方がその
  行より前に定義済みであること、接続用メタデータを検証する。
- **決定**: 同じゾーン同士を結ぶ自己接続は認めない。
- **決定**: `max_link_capacity`は省略時に1とし、指定時は1以上の整数を
  要求する。
- **決定**: `_parse_connection()`は定義済みゾーンの対応を読み取るだけで
  変更せず、ゾーン名をIDへ変換した`Connection`を返す。
- **決定**: 向きを無視した接続ペアの重複検証と解析結果の保存は、複数行の
  状態を管理する`parse_file()`が担当する。
- **理由**: 1つの接続定義の解釈と、既出接続との比較を分離し、各内部
  メソッドが解析状態を直接変更しない構造を保つため。

### DD-031: ゾーン定義と接続定義の混在を許可する

- **決定**: 最初の有効な定義は`nb_drones`でなければならない。
- **決定**: `nb_drones`以降は、ゾーン定義と接続定義が混在することを許可し、
  一度接続が現れた後のゾーン定義を一律には禁止しない。
- **決定**: 各接続が参照する両方のゾーンは、その接続行より前に定義済みで
  なければならない。後の行で定義されるゾーンによる前方参照は許可しない。
- **決定**: `parse_file()`は定義済みゾーンの名前とIDの対応を更新しながら、
  接続行ごとにその時点の対応を`_parse_connection()`へ渡す。
- **決定**: 接続定義が始まったかを示すフェーズやフラグは持たない。
- **理由**: 課題本文が要求するのは各接続先の事前定義であり、無関係なゾーンを
  全接続より前に定義することまでは要求していないため。

### DD-032: 開始・終了ゾーンの重複は出現時に検出する

- **決定**: `parse_file()`は開始ゾーンと終了ゾーンがそれぞれ定義済みかを
  真偽値で管理する。
- **決定**: 2つ目の`start_hub`または`end_hub`が現れた時点で、該当行を示す
  `MapParseError`とする。
- **決定**: ファイル末尾で未定義の開始ゾーンまたは終了ゾーンがあれば、
  行番号を持たないファイル全体の`MapParseError`とする。
- **決定**: 開始・終了ゾーンの名前とIDは通常のゾーンと同様にゾーン一覧と
  名前・ID対応へ保存し、重複検出専用には名前やIDを別途保持しない。
- **理由**: 重複検出には定義済みかどうかだけで十分であり、完成後のID取得は
  `ZoneRole`を持つ`Zone`と`DroneMap`が担当するため。

### DD-033: `parse_file()`は文字列または`Path`を受け取る

- **決定**: 公開メソッドのシグネチャは
  `parse_file(file_path: str | Path) -> Scenario`とする。
- **決定**: 入力を`Path`へ統一し、UTF-8のテキストファイルとして1行ずつ
  コンテキストマネージャーで読み取る。
- **決定**: `FileNotFoundError`、`PermissionError`、`UnicodeDecodeError`などの
  ファイル操作・文字コードに関する標準例外は置き換えない。
- **理由**: 呼び出しやすさと型の明確さを両立し、ファイル全体を不要に
  メモリへ保持せず、標準例外の意味も維持するため。

### DD-034: 名前と色に課題本文以上の文字制限を追加しない

- **決定**: ゾーン名は空でなく、空白と接続区切りの`-`を含まないことを
  要求する。
- **決定**: `color`は空でない単一語であることを要求する。
- **決定**: 英数字だけに限定するなど、課題本文にない文字種制限は追加しない。
- **理由**: 曖昧な箇所へ独自仕様を加えず、課題に記載された条件へ過不足なく
  従うため。

### DD-035: 動的状態を3つの概念的な層に分ける

- **決定**: 動的状態を、個々のドローンの状態、マップ上の使用状況、
  シミュレーション全体の状態という3つの層に分けて考える。
- **決定**: 個々のドローンの状態を、ゾーンや経路の現在の使用状況を求める
  ための正本とする。
- **決定**: 各ゾーンの滞在機数や各経路の通行機数は独立した可変値として
  二重管理せず、ドローンの状態から算出する。
- **決定**: 現在のターン番号など、個々のドローンの状態から算出できない
  動的な値は、シミュレーション全体の状態として扱う。
- **決定**: 3つの層は現時点では責務の整理であり、それぞれを独立したクラスに
  するか、具体的にどの値を持たせるかは今後決める。
- **理由**: 同じ事実を複数箇所で更新することによる不整合を避けながら、
  個体、容量の使用状況、シミュレーション進行の責務を区別するため。

### DD-036: マップの使用状況を独立した可変オブジェクトにしない

- **決定**: 動的状態を管理する中心的なクラスは、1機のドローンを表すクラスと、
  シミュレーション全体を管理するクラスとする。
- **決定**: 既存の`DroneMap`とドローン一覧は、全体管理クラスが同じ階層で
  参照または保持する。`DroneMap`がドローンを子として所有する構造にはしない。
- **決定**: ゾーンの滞在機数や経路の通行機数は、独立した可変オブジェクトに
  保存せず、全体管理クラスがドローン状態から必要時に算出する使い捨ての
  派生値とする。
- **決定**: 使用状況を返す具体的なメソッド名、引数、戻り値は今後決める。
- **理由**: マップとドローンの所有関係、およびドローン状態から使用状況を
  求める算出関係を分け、同じ状態の二重管理を避けるため。

### DD-037: ドローンの状態を3つに大別する

- **決定**: 1機のドローンの状態を、ゾーン滞在中、経路移動中、ゴール済みの
  3つに大別する。
- **決定**: スタート地点で待機しているドローンや、移動できず通常ゾーンで
  待機しているドローンは、どちらもゾーン滞在中として扱う。
- **決定**: スタート地点での待機を独立した状態にはせず、滞在中の
  `zone_id`と`DroneMap`の開始ゾーン情報を組み合わせて判断する。
- **決定**: この決定は状態の意味上の分類であり、各状態を別クラスとして
  実装するかは今後決める。
- **理由**: ドローンの物理的な状況を必要十分な分類で表し、待機理由ごとの
  不要な状態増加を避けるため。

### DD-038: 経路移動中の状態を専用オブジェクトで表す

- **決定**: 経路移動中の状態を`InTransit`としてまとめる。
- **決定**: `InTransit`は、使用中の`connection_id`、移動先を示す
  `destination_zone_id`、到着までの`remaining_turns`を持つ。
- **決定**: 出発元のゾーンIDは重複して保存せず、対象の`Connection`と
  `destination_zone_id`から`Connection.other_zone()`で求める。
- **理由**: 移動中にだけ必要な値を他の状態へ持たせず、経路上の進行方向も
  重複のないデータで表現するため。

### DD-039: 滞在中とゴール済みも状態オブジェクトで表す

- **決定**: ゾーン滞在中の状態を`AtZone`としてまとめ、現在滞在している
  `zone_id`を持たせる。
- **決定**: ゴール済みの状態を`Finished`としてまとめ、付随データは
  持たせない。
- **決定**: `zone_id`は全状態に共通する値ではないため、`Drone`本体ではなく
  `AtZone`だけに持たせる。
- **決定**: ドローンのIDなど、すべての状態に共通する情報は状態オブジェクト
  ではなく`Drone`本体に持たせる。
- **理由**: 各状態で存在するデータだけを保持し、移動中にも現在のゾーンが
  あるように見える矛盾を避けるため。

### DD-040: 移動判断とドローンの状態変更を分担する

- **決定**: 移動可能かどうかの判断は、マップ、ゾーンと経路の使用状況、
  対象ドローンの状態を参照できる全体管理クラスが担当する。
- **決定**: `Drone`は、許可された移動を自身の状態遷移として実行する
  メソッドを持つ。
- **決定**: 外部からの移動要求は全体管理クラスを窓口とし、全体管理クラスが
  検証と必要値の決定を行った後に、`Drone`の状態変更メソッドを呼び出す。
- **決定**: `Drone`は自身の現在状態に関する最低限の前提を確認するが、
  マップ接続、ゾーン容量、経路容量などの全体条件は判断しない。
- **理由**: 移動する個体の責務と周囲を含むルール判断を分離しつつ、検証を
  経由しない不正な移動操作を防ぎやすくするため。

### DD-041: ドローンの状態更新を2つの操作にまとめる

- **決定**: `Drone`の主な状態更新操作を、移動を開始する`start_move()`と、
  移動を1ターン進める`advance_one_turn()`の2つとする。
- **決定**: `start_move()`は、許可済みの移動情報を受け取り、`AtZone`から
  `InTransit`へ状態を変更する。
- **決定**: `advance_one_turn()`は、残りターンが2以上なら1減らし、残り
  1ターンなら到着処理まで同じ呼び出し内で完了する。
- **決定**: 到着先が終了ゾーンかどうかは、`DroneMap`を参照できる全体管理
  クラスが判定し、その判定結果を`advance_one_turn()`へ渡す。
- **決定**: `Drone`自身には`DroneMap`を保持させず、`advance_one_turn()`は
  渡された判定結果に従って`AtZone`または`Finished`へ状態を変更する。
- **決定**: 到着だけを行う3つ目の公開操作は現時点では設けない。
- **理由**: マップを使う判断と個体の状態変更という責務分担を一貫させ、
  残り0ターンの移動中という中途半端な状態を作らないため。

### DD-042: `Drone`は状態遷移の可否を検証する

- **決定**: `Drone`の状態変更メソッドは、呼び出された操作が現在の状態から
  実行可能かを検証する。
- **決定**: 移動開始は現在の状態が`AtZone`の場合だけ許可し、`InTransit`または
  `Finished`の場合は拒否する。
- **決定**: 1ターン進める操作は現在の状態が`InTransit`の場合だけ許可し、
  `AtZone`または`Finished`の場合は拒否する。
- **決定**: マップ上の接続、容量、ゾーンの性質など、`Drone`単体では分からない
  条件は全体管理クラスが検証する。
- **決定**: IDや残りターン数など個々の値の妥当性は、状態遷移の可否とは分け、
  各データオブジェクトの生成時検証として今後詳細を決める。
- **理由**: `Drone`が知り得る範囲で自身の整合性を守り、全体ルールの検証を
  重複させないため。

### DD-043: ドローンと状態オブジェクトの単体値を検証する

- **決定**: `Drone.id`、`AtZone.zone_id`、`InTransit.connection_id`、
  `InTransit.destination_zone_id`は、各オブジェクトの生成時に1以上の整数で
  あることを検証する。
- **決定**: `InTransit.remaining_turns`は、生成時に1以上の整数であることを
  検証する。
- **決定**: `Drone.state`は`AtZone`、`InTransit`、`Finished`のいずれかとする。
- **決定**: `start_move()`は状態の検証に加え、移動先のゾーンIDが現在滞在中の
  ゾーンIDと異なることを検証する。
- **決定**: IDの実在、ドローンIDの重複、接続関係、容量、マップから決まる
  正しい移動ターン数は、複数オブジェクトを扱う全体管理クラスが検証する。
- **理由**: 単体で確認できる不正値と状態矛盾を生成元で防ぎ、マップ全体の
  検証とは明確に分離するため。

### DD-044: 全体管理クラスが保持するデータを3つに絞る

- **決定**: 全体管理クラスは、`drone_map`、全ドローンをまとめた`drones`、
  現在のターン番号を示す`current_turn`を保持する。
- **決定**: ドローン数は別の可変値として重複保存せず、`drones`の要素数から
  算出する。
- **決定**: `Scenario.drone_count`は初期ドローンを生成するために使い、全機の
  初期状態を開始ゾーンの`AtZone`とする。
- **決定**: `current_turn`の初期値は0とする。
- **決定**: ゾーン・経路の使用数や移動履歴は、現時点では全体管理クラスの
  保持データに加えない。
- **理由**: 静的マップ、動的な個体状態、全体の進行状態だけを正本として保持し、
  算出可能な情報の二重管理を避けるため。

### DD-045: ドローンをID索引付きの辞書で管理する

- **決定**: 全体管理クラスの`drones`は、ドローンIDをキー、対応する`Drone`
  インスタンスを値とする辞書として管理する。
- **決定**: 辞書は`Scenario.drone_count`を基に全体管理クラスが内部で生成し、
  各キーと対応する`Drone.id`を一致させる。
- **決定**: `Drone.id`は生成後に変更できない識別情報とし、`Drone.state`だけを
  シミュレーション中に変更可能とする。
- **決定**: 辞書のキーは検索用の索引、`Drone.id`は個体自身の識別情報として
  扱う。
- **理由**: IDによる直接検索を可能にしながら、辞書のキーと個体IDの不整合を
  防ぐため。

### DD-046: `SimulationState`を`Scenario`から初期化する

- **決定**: 全体管理クラスの名前を`SimulationState`とし、コンストラクタは
  `Scenario`を受け取る。
- **決定**: `SimulationState`は`Scenario.drone_map`を自身の`drone_map`として
  保持するが、`Scenario`自体は保持し続けない。
- **決定**: `Scenario.drone_count`に従ってIDを1から順に割り当てた`Drone`を
  生成し、全機の初期状態を開始ゾーンの`AtZone`とする。
- **決定**: 生成したドローンをID索引付きの`drones`へ格納し、`current_turn`を
  0で初期化する。
- **理由**: パーサーの出力からシミュレーションの初期状態を一意に構築し、
  初期化後に不要となるドローン数の重複保持を避けるため。

### DD-047: 現在状態から算出できる3つを基礎参照メソッドとする

- **決定**: `SimulationState`は、指定ゾーンに現在滞在しているドローン数、
  指定経路を現在移動中のドローン数、全ドローンがゴール済みかを算出する
  3つの基礎参照メソッドを持つ。
- **決定**: これらの結果は別の可変値として保存せず、呼び出し時の`drones`から
  算出する。
- **決定**: 指定ゾーンにあと何機入れるか、または進入可能かという判定は、
  同一ターンに予定される退出と進入にも依存するため、現時点では基礎参照
  メソッドに含めない。
- **決定**: 移動計画を考慮する容量判定の具体的な形は、ターン処理と
  スケジューリングアルゴリズムを設計するときに決める。
- **理由**: 現在状態の事実を返す汎用的な処理と、移動計画に依存する方針判断を
  分離し、アルゴリズム確定前の過剰なインターフェース追加を避けるため。

### DD-048: 不正なドローン状態遷移に独自例外を使う

- **決定**: `FlyInError`を継承する`DroneStateError`を追加する。
- **決定**: `start_move()`または`advance_one_turn()`が現在の状態では実行
  できない場合、`DroneStateError`を送出する。
- **決定**: 1以上であるべきIDや残りターン数など、単体値の不正には
  `ValueError`を使う。
- **決定**: 存在しないドローン、ゾーン、経路のID指定には`KeyError`を使う。
- **決定**: `DroneStateError`は現時点では追加の属性や独自メソッドを持たない。
- **理由**: 不正な値、不明な参照、不可能な状態遷移を例外の種類で区別し、
  Fly-in固有の状態操作エラーを呼び出し側が識別できるようにするため。

### DD-049: 動的状態の公開方法と基礎メソッドの形を確定する

- **決定**: `AtZone`、`InTransit`、`Finished`は生成後に変更できない状態
  オブジェクトとし、`Drone`は新しい状態オブジェクトへの差し替えで状態を
  更新する。
- **決定**: `Drone.id`と現在の`state`は外部から参照可能にするが、直接代入は
  許可せず、状態変更は`Drone`の公開メソッドを通して行う。
- **決定**: `SimulationState`のマップ、ドローン集合、現在ターンは外部から
  参照可能にするが、内部の辞書や値を外部から直接変更できない形で公開する。
- **決定**: `Drone.start_move(connection_id, destination_zone_id, travel_turns)`は
  状態を更新し、戻り値を返さない。
- **決定**: `Drone.advance_one_turn(destination_is_goal)`は状態を更新し、
  戻り値を返さない。
- **決定**: `SimulationState`の基礎参照メソッド名と戻り値を、
  `get_zone_occupancy(zone_id) -> int`、
  `get_connection_occupancy(connection_id) -> int`、
  `all_drones_finished() -> bool`とする。
- **理由**: 呼び出し側が状態を観察できる一方、確定した検証と状態遷移を
  迂回した直接変更を防ぎ、公開インターフェースを実装前に固定するため。

### DD-050: 1ターンの新規移動を値オブジェクトで表す

- **決定**: 現在`AtZone`にいる1機が、そのターンに開始しようとする移動を
  `MoveIntent`で表す。
- **決定**: `MoveIntent`は`drone_id`と`destination_zone_id`を持つ、生成後に
  変更できないデータクラスとする。
- **決定**: そのターンに開始する複数の`MoveIntent`を`TurnPlan`にまとめ、
  `moves`を変更不能なタプルとして持たせる。
- **決定**: 待機する`AtZone`、自動的に進行する`InTransit`、および`Finished`の
  ドローンは`TurnPlan`に含めない。
- **決定**: `MoveIntent`は各IDが1以上の整数であることを生成時に検証し、
  `TurnPlan`は同一ドローンIDの重複を生成時に拒否する。
- **決定**: 両クラスには現時点で公開メソッドを設けず、移動可能性、容量、
  計画の実行は`SimulationState`などの全体側の責務とする。
- **理由**: 現在状態と重複する値や容量の予測結果を計画へ保存せず、移動意思と
  その検証・実行を分離するため。

### DD-051: 計画を現在状態へ反映する前に仮実行できるようにする

- **決定**: `TurnPlan`をただちに`SimulationState`へ反映する方式ではなく、
  現在状態を変更せずに次ターンの仮結果を計算できる方式を採用する。
- **決定**: 複数の計画候補がある場合は、同じ`SimulationState`を基準に各候補の
  仮結果を作成し、選択された計画だけを実際の状態へ反映できる構造とする。
- **決定**: 仮結果は可変な`SimulationState`の複製ではなく、変更不能な軽量の
  値オブジェクトとして表現する。
- **決定**: 仮実行機能は候補比較を必須にはせず、単一計画の事前検証にも利用
  できる汎用的な仕組みとする。
- **決定**: 仮結果オブジェクトの名前、保持データ、検証失敗の表現は今後決める。
- **理由**: 可変なドローン状態の複製や巻き戻しを避け、アルゴリズムが必要に
  応じて安全に計画を比較または検証できるようにするため。

### DD-052: 経路容量をそのターンの全使用者で検証する

- **決定**: 経路容量はターン終了時に経路上へ残るドローン数ではなく、その
  ターン中に経路を使用するドローン数で検証する。
- **決定**: 各経路の使用者を、ターン開始時点でその経路を`InTransit`中の
  ドローンと、`TurnPlan`によってそのターンに新しくその経路へ入るドローンの
  和として求める。
- **決定**: そのターンに目的ゾーンへ到着するドローンも、到着のために経路を
  使用するため使用者に含める。
- **決定**: 使用者はドローンIDの集合として扱い、同じドローンを重複して
  数えない。
- **理由**: 1ターン移動や複数ターン移動の到着ターンでは、終了状態だけを
  数えると実際の経路使用を見落とすため。

### DD-053: 仮実行結果に終了状態とターン中の経路使用を残す

- **決定**: 仮実行結果を表す変更不能な値オブジェクトを`TurnProjection`と
  呼ぶ。
- **決定**: `TurnProjection`は、作成元のターン番号、仮実行した`TurnPlan`、
  ターン終了時の全ドローン状態、このターンの経路使用状況を持つ。
- **決定**: 経路使用状況は単なる使用数ではなく、経路IDごとの使用ドローンID
  集合として表し、各集合の要素数から使用数を求められるようにする。
- **決定**: `TurnProjection`は`DroneMap`、可変な`Drone`インスタンス、作成元の
  `SimulationState`自体を保持しない。
- **決定**: 作成元の全ドローン状態を重複して保存するか、仮結果を実状態へ
  直接適用するかは現時点では確定しない。
- **理由**: 終了時の配置だけでは見えなくなる1ターン移動や到着ターンの
  経路使用を保持し、容量検証、候補比較、後の出力に再利用するため。

### DD-054: `TurnProjection`は計算済み結果の保持と単体検証だけを担う

- **決定**: 仮状態と経路使用状況の計算、およびマップを必要とする検証は、
  `SimulationState.preview_turn()`が担当する。
- **決定**: `TurnProjection`は仮実行を行わず、渡された計算済み結果を変更不能な
  形で保持する値オブジェクトとする。
- **決定**: `TurnProjection`は、作成元ターンが0以上の整数であること、計画・
  ドローン状態・経路使用者の型とID、保持データ間の参照整合性など、自身の
  データだけで完結する検証を行う。
- **決定**: 外部から渡された可変な辞書や集合はそのまま保持せず、内部用に
  コピーしたうえで読み取り専用または変更不能な形にする。
- **決定**: IDのマップ上での実在、接続関係、移動コスト、ゾーン容量、経路容量
  など、`DroneMap`が必要な検証は`TurnProjection`では行わない。
- **理由**: 仮結果を`SimulationState`から独立させたまま、壊れた形式や外部からの
  後変更を防ぎ、計算責務との境界を明確にするため。

### DD-055: `TurnProjection`の単体検証範囲を定める

- **決定**: `source_turn`は0以上の整数とし、真偽値は整数として認めない。
- **決定**: `plan`は`TurnPlan`でなければならない。
- **決定**: `projected_drone_states`は空でないID・`DroneState`対応とし、
  ドローンIDは1以上の整数、状態は`AtZone`、`InTransit`、`Finished`の
  いずれかでなければならない。
- **決定**: `connection_users`は1以上の経路IDから`frozenset`への対応とし、
  集合内の各ドローンIDは1以上の整数でなければならない。
- **決定**: `plan`と`connection_users`に登場する全ドローンIDは、
  `projected_drone_states`にも存在しなければならない。
- **決定**: 1機のドローンIDが複数経路の使用者集合に現れることを禁止し、
  `plan`内の各ドローンは、いずれか1つの経路使用者集合に含まれることを
  要求する。
- **決定**: `Mapping`のキーと`frozenset`の要素は構造上重複しないため、
  各コンテナ内部の重複検証は追加しない。
- **理由**: マップを参照せず確認できる形式と内部整合性だけを保証し、
  マップ依存の検証を`preview_turn()`へ残すため。
