# Fly-in 課題要件整理

## 1. 文書情報

- 課題名: `Fly-in`
- 課題概要: 複数のドローンを接続されたゾーン群の中で移動させ、各種制約を守りながら、全機が開始地点から終了地点へ到達するまでのシミュレーションターン数を最小化する。
- 課題本文バージョン: 1.6
- 実装言語: Python 3.10 以上

## 2. 最終成果物

Git リポジトリ内に、少なくとも次のものを提出する。

1. 指定形式の入力ファイルを読み取るパーサー
2. 移動規則、ゾーン占有規則、容量制約を守るシミュレーションエンジン
3. 総ターン数の最小化を目指す経路探索アルゴリズム（1つ以上）
4. 色付きターミナル表示またはグラフィカルインターフェースによる視覚表現
5. 指定形式に従うターミナル出力またはログ出力
6. 必須ルールを備えた `Makefile`
7. 指定内容を満たす英語の `README.md`
8. Python の生成物を除外する `.gitignore`

評価対象になるのは Git リポジトリ内のファイルだけである。課題本文は、提出ファイルをリポジトリのルートへ配置するよう求めている。

## 5. 入力ファイル形式

### 5.1 全体構造

- 1行目は必ず、正の整数によるドローン数の定義でなければならない。

  ```text
  nb_drones: <positive_integer>
  ```

- プログラムは任意のドローン数を扱えなければならない。
- 開始ゾーン `start_hub:` はちょうど1つ必要である。
- 終了ゾーン `end_hub:` はちょうど1つ必要である。
- コメントは `#` から始まり、無視する。
- 座標は常に整数である。

### 5.2 ゾーン定義

```text
start_hub: <name> <x> <y> [metadata]
end_hub: <name> <x> <y> [metadata]
hub:       <name> <x> <y> [metadata]
```

- `start_hub:` は開始ゾーンを表す。
- `end_hub:` は終了ゾーンを表す。
- `hub:` は通常のゾーン定義を表す。
- ゾーン名は一意でなければならない。
- ゾーン名には、ダッシュ `-` と空白以外の有効な文字を使用できる。
- メタデータは任意で、角括弧 `[...]` 内に記述する。
- 同じメタデータブロック内のタグ順序は任意である。

ゾーン用メタデータ:

| キー | 既定値 | 要件 |
| --- | --- | --- |
| `zone=<type>` | `normal` | `normal`、`blocked`、`restricted`、`priority` のいずれか。その他は解析エラー。 |
| `color=<value>` | なし | 任意の有効な単一語文字列。固定された許可色一覧はない。 |
| `max_drones=<number>` | `1` | 同時にゾーンを占有できる最大ドローン数。正の整数でなければならない。 |

- 開始ゾーンと終了ゾーンの収容数は無制限である。
- 開始ゾーンまたは終了ゾーンに `max_drones` が指定されていても無視し、解析エラーにはしない。

### 5.3 ゾーン種別

| 種別 | 移動コストと意味 |
| --- | --- |
| `normal` | 標準ゾーン。進入コストは1ターン。既定値。 |
| `blocked` | 進入も通過もできない。これを使う経路は無効。 |
| `restricted` | 機密・危険ゾーン。進入コストは2ターン。 |
| `priority` | 優先ゾーン。進入コストは1ターンで、経路探索時に優先すべきゾーン。 |

### 5.4 接続定義

```text
connection: <name1>-<name2> [metadata]
```

- 接続は2つのゾーン間の双方向エッジである。
- 接続先は、接続行より前に定義済みのゾーンだけでなければならない。
- ゾーン名にダッシュを使用できないのは、この構文で名前を区切るためである。
- 接続用メタデータは任意で、角括弧 `[...]` 内に記述する。
- `max_link_capacity=<number>` は、同一接続を同時に通過できる最大ドローン数を表す。既定値は `1` で、指定値は正の整数でなければならない。
- 同じ接続を複数回定義してはならない。`a-b` と `b-a` は重複と見なす。

### 5.5 パースエラー

- ゾーンおよび接続のメタデータブロックは構文的に正しくなければならない。
- 無効なゾーン種別、非正数の容量、重複、不明な接続先など、あらゆる解析エラーでプログラムを停止する。
- エラーメッセージには、エラーが発生した行と原因を明確に示す。
- 提供マップだけでなく、独自マップを作成してエッジケースとエラー処理を確認することが強く推奨される。

## 6. 経路探索要件

主目的は、すべてのドローンを開始ゾーンから終了ゾーンへ移動させるまでの総シミュレーションターン数を最小化することである。

アルゴリズムは次を満たす必要がある。

- 複数のドローンを同時に移動させる。
- スループットを最大化し、不要な遅延を避けるように経路と移動をスケジュールする。
- 複数経路へドローンを分配する。
- 移動できない場合には戦略的に待機させる。
- 経路の衝突とデッドロックを回避する。
- ゾーン種別による移動コストを含む経路長を考慮する。
- ドローン同士の衝突や相互ブロックを防ぐターンスケジューリングを行う。
- グラフ構造を調べ、独立した経路と重複する経路を扱う。
- ゾーン容量 `max_drones` と接続容量 `max_link_capacity` を考慮する。
- トポロジーやゾーン種別が異なるマップに応じ、異なる経路戦略を使用できる適応性を持たせる。
- 多数のドローンを扱えるようにする。

評価時には、計算量、パスの再計算またはキャッシュ、メモリ使用量、アルゴリズムの効率を説明できる必要がある。

## 7. ゾーン占有規則

- 通常、各ゾーンを同一ターンに占有できるドローンは最大1機である。
- `max_drones=N` があるゾーンは、最大 `N` 機まで同時に占有できる。
- 開始ゾーンでは、初期状態に限らず全ドローンが同じ空間を共有できる。
- 終了ゾーンには複数機が到着でき、到着したドローンは配送完了として扱う。
- ゾーン容量が許可しない限り、同じターンに2機以上が同じゾーンへ進入してはならない。
- 移動先ゾーンの最大容量を超える移動は禁止する。
- 接続の `max_link_capacity` を超える数のドローンが、同一ターンにその接続を通過してはならない。
- すべてのゾーン容量と接続容量を守る限り、複数のドローンは同時に移動できる。
- あるターンにゾーンから出るドローンは、その同じターン中にゾーン容量を解放する。
- 移動後に出発するドローンの分を解放した状態で、移動先に空き容量がなければならない。

## 8. ターンと移動の規則

シミュレーションは離散的なターン単位で進行する。各ターンに各ドローンは次のいずれかを行える。

1. 容量制約が許せば、隣接する接続済みゾーンへ移動する。
2. `restricted` ゾーンへ向かう接続上へ移動し、2ターン移動を開始する。
3. 移動できない、または待機が必要な場合に現在位置へ留まる。

通常の1ターン移動:

- 移動コストは、出発ゾーンではなく移動先ゾーンの `zone` 種別で決まる。
- `normal` および `priority` への進入には1ターンかかる。

`restricted` への2ターン移動:

- 1ターン目に、ドローンは `restricted` ゾーンへ向かう接続上へ移動する。
- ドローンは移動中、その接続を占有する。
- 次のターンに必ず目的の `restricted` ゾーンへ到着しなければならない。
- 接続上で追加ターンを待機してはならない。
- 到着ターンに移動先ゾーンの空き容量が必要である。この制約を満たせるよう事前にスケジュールする必要がある。

シミュレーションは全ドローンが終了ゾーンへ到達した時点で終了する。

## 9. シミュレーション出力形式

- シミュレーションのターンごとの移動を出力する。
- 1行が1ターンを表す。
- そのターンに発生した全移動を、空白区切りで同じ行に出力する。
- ゾーンへ移動した場合の形式は `D<ID>-<zone>` とする。
- `restricted` ゾーンへ向けて飛行中の場合の形式は `D<ID>-<connection>` とする。
- `D<ID>` は `D1`、`D2` のような一意のドローン識別子である。
- そのターンに動かないドローンは出力しない。
- 終了ゾーンに到達したドローンは配送済みとし、それ以降追跡しない。

課題本文の出力例:

```text
D1-roof1 D2-corridorA
D1-roof2 D2-tunnelB
D1-goal D2-goal
```

## 10. 視覚表現

次のいずれか、または両方を実装する。

- ドローンの移動とゾーン状態を示す色付きターミナル出力
- ネットワークとドローン位置を表示するグラフィカルインターフェース

ゾーンに `color` が指定されている場合、色付きターミナル出力またはグラフィカル表示によって視覚的なフィードバックを提供する。表示がシミュレーションの理解をどのように助けるか説明できる必要がある。

## 11. 正しいシミュレーションの条件

有効なシミュレーションは、次のすべてを満たす。

- すべての移動規則と占有規則に従う。
- ゾーン種別による移動コストを正しく扱う。
- ゾーン容量と接続容量を守る。
- 容量超過など、すべての衝突を回避する。
- 全ドローンが開始ゾーンから終了ゾーンへ到達する。

主要評価指標は、全ドローンの配送に必要な総ターン数である。少ないほど高評価となる。同一ターン数の場合、任意の副次評価指標またはコード品質で比較される場合がある。

任意の副次評価指標:

- 1ターン当たりに移動したドローン数
- ドローン1機当たりの平均ターン数
- 全ドローンの重み付き移動コスト合計
- 視覚表現の品質と有用性

副次評価指標を自動計算することは必須ではないが、ピア評価を助けるため出力または文書へ掲載することが推奨される。

## 16. 課題本文だけでは完全に定義されていない点

以下は実装時に一貫した仕様を決め、`README.md` またはコード内で説明し、テストする必要がある。

- `D<ID>-<connection>` における接続名の厳密な文字列表現は明記されていない。
- 双方向接続で、互いに逆方向へ同時移動するドローンを `max_link_capacity` 上どのように数えるかは明記されていない。
- `priority` は「経路探索で優先すべき」とされるが、同コスト経路に対する厳密なタイブレーク規則はない。
- 空行、行末コメント、重複メタデータキー、未知のメタデータキーなどに対する受理・拒否規則は明記されていない。
- 不正入力時の終了コードやエラーメッセージの厳密な書式は指定されていない。ただし、処理を停止し、行と原因を明示する必要がある。
- 通常の移動出力と色・補助情報を同時に表示する場合、機械判定可能な出力と視覚表示を分離する方法は指定されていない。

これらの未定義点について独自仕様を設ける場合も、本文で明示された規則と矛盾してはならない。
